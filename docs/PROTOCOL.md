本文记录 `switch-net-fix` 依赖的全部事实，包括观察方法、原始现象和边界。

每条事实都标注来源等级，阅读时请对照：

|---|---|

| **官方** | 腾讯官方公告、任天堂官方支持页原文，可点开核对（§9.1） |
| **第三方** | 媒体或社区文章，未经官方确认，仅供参证（§9.3、§9.4） |

## 2. 观察方法

不用破解、不改固件，只在同一局域网内用明文 HTTP 代理观察主机行为：

1. PC 上监听一个 HTTP 代理端口
2. Switch 的 Wi-Fi 设置里把代理指向该端口
3. 触发连接测试或软件更新
4. 记录代理收到的 `CONNECT` / 请求行

因为连接自检走的是**明文 HTTP**，代理可以直接看到目标域名甚至伪造响应，无需安装证书。

## 3. 观察到的请求

停服后，主机在联网场景下发出的请求（2026-10-31 全量抓取，覆盖连接测试、
软件更新与主机系统更新三种触发方式）：

| 目标 | 协议 | 用途 | 现状 |
|---|---|---|---|
| `ctest.cdn.n.nintendoswitch.cn:80` | HTTP（明文） | 连接自检 | 域名已注销，可伪造 |
| `api.hac.lp1.ctest.srv.n.nintendoswitch.cn:443` | HTTPS | 自检 API（自检通过后的第二轮校验） | 域名已注销 |
| `sun.hac.lp1.d4c.n.nintendoswitch.cn:443` | HTTPS | **系统更新元数据**（`/v1/system_update_meta`） | 域名已注销 |
| `aqua.hac.lp1.d4c.n.nintendoswitch.cn:443` | HTTPS | **系统更新必须性判定**（`/required_system_update_meta`） | 域名已注销 |
| `Service-status-lp1.cdn.n.nintendoswitch.cn:443` | HTTPS | 服务状态查询 | 域名已注销 |
| `dauth-lp1.ndas.srv.n.nintendoswitch.cn:443` | HTTPS | 设备 / 账号认证 | 域名已注销 |

**关键观察：全程没有出现任何 `*.nintendo.net` 请求。** 任天堂全球 CDN 域名
（`atum.hac.lp1.d4c.nintendo.net` 等）在境内可以正常解析到 Akamai 节点，
但国行主机从不向它们发起请求——它的整条链路都指向腾讯自建的服务。

这意味着不存在"把流量改道到全球服务器"的空间：主机压根不知道那些地址。

`sun` 与 `aqua` 两条是**系统更新流程的专属端点**，见第 8 节：它们的存在证明
更新流程确实会走到网络这一步，但它拼出的主机名恒为 `.cn` 后缀。

## 4. 连接自检协议

主机向 `http://ctest.cdn.n.nintendoswitch.cn/` 发起 `GET`，期望的响应必须同时满足：

```
HTTP/1.1 200 OK
Content-Type: text/plain
X-Organization: Nintendo
Content-Length: 2

ok
```

四项缺一不可：

1. 状态码 `200`
2. 响应体恰好是 `ok`（2 字节，无换行）
3. `Content-Type: text/plain`（**不能**带 `; charset=...`）
4. `X-Organization: Nintendo`

第 4 项最容易漏。缺它会看到主机**每 3 秒重试一次**、持续时间无限，
而不是立刻失败——这个特征可用于判断响应是否被接受。

## 5. 边界：认证无法伪造

自检通过后，主机会紧接着请求：

```
CONNECT dauth-lp1.ndas.srv.n.nintendoswitch.cn:443
```

这是 HTTPS 设备认证，需要腾讯签发的证书与在线服务端。两者都已不存在，
因此**在原理上不可能伪造**，也不是"努力一下就能绕"的问题。

由此得到的结论：

| 能力 | 是否可能 |
|---|---|
| 让主机显示"互联网：已连接" | ✅ 明文 HTTP，可伪造 |
| 消除"需要连接互联网"的拦截弹窗 | ✅ |
| 恢复 eShop | ❌ 服务端与证书均不存在 |
| 恢复游戏更新下载 | ❌ 同上 |
| 恢复在线联机 | ❌ 同上 |
| 恢复云存档 | ❌ 国行从未提供 |

```bash

```

## 8. 为什么不能把系统更新改指到国际服

「把固件更新地址换成国际服」是收到过最多的请求。它不成立，原因不在配置，
而在固件与 PKI 两层。

### 8.1 主机走哪个 CDN，由固件里的区域标志决定，不由 DNS 决定

Switch 的 CDN URL 结构统一为：

```
{server_name}.hac.{environment}.{serverset}.{host}
```

其中 `{host}` 二选一（来源：switchbrew *Network* 条目）：

| `{host}` | 含义 |
|---|---|
| `nintendo.net` | 全球 CDN |
| `n.nintendoswitch.cn` | 中国 CDN |

系统更新走 `sun` 服务：

```
https://sun.hac.{env}.d4c.{host}/v1/system_update_meta?device_id=...
```

响应是 JSON，`system_update_metas` 里给出一个 `title_id` 与 `title_version`，
主机据此去 `atum`/`atumn` 拉系统包。

国行机的区域固定为「中国大陆」，设置里该项为灰色不可改。因此 `{host}`
恒为 `n.nintendoswitch.cn`，**这是编译进系统的分支，不是 DNS 解析结果**。
想让主机去 `nintendo.net`，只能改固件。

### 8.2 任天堂 CDN 的证书由自建 CA 签发，公网信任库不认

实测直连 `sun.hac.lp1.d4c.nintendo.net:443` 取到的证书：

| 字段 | 值 |
|---|---|
| subject | `Nintendo Co., Ltd.` (Kyoto) |
| SAN | `*.cdn.nintendo.net` |
| issuer | `Nintendo of America, Inc.` / `Nintendo Class 2 CA - G3` |
| 有效期 | 2023-03-02 → 2037-12-31 |

签发者是任天堂**自己的私有 CA**，根证书只内置在主机固件里。这意味着：

- 用公网证书（Let's Encrypt、DigiCert、自签）冒充 → 主机不认
- 用本地代理做 TLS 中间人 → 主机不认，且需要往主机装根证书（零售机做不到）
- 把国行域名解析到任天堂真实节点 → 证书 SAN 不匹配该域名，握手即断

### 8.3 四层证据汇总

| 层 | 需要的条件 | 实测结果 |
|---|---|---|
| 区域标志 | 固件切到全球分支 | 国行锁定「中国大陆」，界面不可改 |
| DNS | `*.nintendoswitch.cn` 可解析 | 记录已清空，任意子域 `Non-existent domain` |
| TLS | 目标持有国行域名的有效证书 | 任天堂节点证书 SAN 仅 `*.cdn.nintendo.net`，域名不匹配 |
| 内容 | 国行签名的系统包 | 海外包与国行包不可混用，官方与媒体均确认 |

四层没有一层可以通过局域网内的配置绕过。真要跨过去，等于修改固件、
绕过签名校验，属于破解范畴，本项目不涉及。

### 8.4 记一笔：系统更新数据与游戏更新数据不同

游戏的更新数据在「设置 → 数据管理 → 软件的详细管理」里可以删除（见 README
常见问题）。**系统更新数据不在该列表中**，一旦触发下载并中断，用户侧没有
清理入口。因此不要为了探测去点「设置 → 主机 → 系统更新」。

注：若更新流程在 `sun` 的 TLS 阶段就被拦下（本工具的默认行为），一个字节都
不会下载，不会产生残留数据。风险在于把它接到一个"看起来能连通"的伪造端点。

### 8.5 实证：主机在系统更新时确实只拼 `.cn` 后缀

2026-10-31 的一次完整抓取（自检通过后立即触发「系统更新」）：

```
[08:03:48] ctest.cdn.n.nintendoswitch.cn/                          [伪造成功]
[08:05:56] api.hac.lp1.ctest.srv.n.nintendoswitch.cn:443          [国服 HTTPS]
[08:12:56] sun.hac.lp1.d4c.n.nintendoswitch.cn:443                [国服 HTTPS]
[08:13:01] sun.hac.lp1.d4c.n.nintendoswitch.cn:443                [国服 HTTPS]
[08:13:05] Service-status-lp1.cdn.n.nintendoswitch.cn:443         [国服 HTTPS]
[08:13:57] dauth-lp1.ndas.srv.n.nintendoswitch.cn:443             [国服 HTTPS]
```

自检一通过，主机立刻按 `ctest → sun → aqua → dauth` 的顺序推进，
**每一条都是 `.cn` 后缀，零条 `nintendo.net`**。这是 §8.1 的直接实证：
后缀由固件决定，改 DNS 不会改变主机要拼的字符串。

### 8.6 版本号事实：23.x 是海外版的版本，与国行无关

| 版本 | 发布日期 | 归属 |
|---|---|---|
| 19.0.1 | 国行停服前倒数第二版 | 国行（用户机器所在） |
| 19.0.2 | 2026-01 | 国行最后一版，官方称"提升稳定性" |
| 23.0.0 | 2026-09-10 | 全球（含初代 Switch 与 Switch 2） |
| 23.0.1 | 2026-10-01 | 全球，修复 23.0.0 的启停卡顿 |

国行停在 19.0.2，与 23.x 相差 4 个大版本。23.x 的新功能（虚拟游戏卡设置、
NS2 完整传送、TV 模式 VRR）都依赖国行从未提供的服务。**国行机不存在任何
可到达 23.x 的渠道**：官方通道已关，跨区安装需要改固件。

另据 switchbrew 记录，2026-10-13 前后起 23.0.0 已成为海外 `dauth` 的强制
要求——那是海外机在线的前置条件，与国行无关（国行 `dauth` 已随停服消失）。

完整的版本谱系（含 20.x / 21.x 中间版本与 20.0 这道门槛）见 **§9.2**。

### 8.7 反证实验：把 `.cn` 真的映射到全球节点，主机 362ms 后自己断开

有人会问："直接把域名换成全球的不就行了？"为此做过一次真实实验：
在 PC 上起一个透明转发代理，把主机的

```
sun.hac.lp1.d4c.n.nintendoswitch.cn:443
```

映射成 `sun.hac.lp1.d4c.nintendo.net:443`，**TCP 直连任天堂真实节点，
不做任何 TLS 中间人**，主机看到的就是任天堂服务器原样吐出的字节。

结果（2026-10-31 实测）：

```
#1  === sun.hac.lp1.d4c.n.nintendoswitch.cn => sun.hac.lp1.d4c.nintendo.net:443  TCP 已连通
#1  C→S    517B  Handshake   SNI_命中=True          ← ClientHello，SNI 仍是 .cn
#1  S→C   2769B  Handshake   (ServerHello 起始)      ← 服务器 4.2 秒后回话
#1  C→S     24B  AppData                             ← 362ms 后，主机发了 24 字节
#1  C→S 关闭
#1  === 合计 C→S 541B / S→C 2769B
```

**24 字节是判据。** TLS 1.3 的记录格式为 `5B 头 + AEAD(内容+1B 类型) + 16B tag`：

| 主机若在发什么 | 计算 | 长度 |
|---|---|---|
| 加密 Alert（fatal，证书被拒） | 5 + (1 层 + 1 描述 + 1 类型) + 16 | **24B** |
| Finished（握手成功的第一步） | 5 + (32 verify_data + 1 类型) + 16 | 54B |
| Finished + HTTP 请求（真突破） | 54 + 300 以上 | 350B+ |

实测上行 = 517（ClientHello）+ **24** = 541B。服务器回的 2769B 是
`ServerHello + Certificate + CertificateVerify + Finished` 一整趟。

结论：主机**完整收到了证书**，用 362 ms 做完校验，判定不受信任，发出
24 字节的加密 Alert 后断开——**从头到尾没发过 Finished，更没发过 HTTP 请求**。

那 2769B 里装的是什么证书？拿同一个 `.cn` SNI 直连该节点取到的证书为：

```
subject : a248.e.akamai.net
SAN     : *.akamaihd-staging.net / *.akamaized.net ...
issuer  : DigiCert Global G3 TLS ECC SHA384 2020 CA1
```

即 Akamai 的兜底证书。任天堂节点按 SNI 找不到 `.cn` 对应的证书时，
回落成一张与请求主机名完全无关的证书，主机自然拒绝。

**这条实验把 §8.3 的 TLS 一行从推论变成了实测**，并证明不存在
"换个地址就行"的空间：地址能换，证书换不了。

### 9.3 「有博主把国行机升到 23」的真相（来源等级：第三方，但可交叉验证）

结论：**那些教程全部是破解机操作，且第一步是改固件的区域标志，不是换服务器地址。**

出处一：《Switch 大气层 1.12.0 系统 + 23.0.0 固件升级 软硬破解通用图文教程》
（`91switch.com/articles/1994`）。原文两句关键话：

> 「**国行机器需要先转换为国际版之后再升级**，不然会成砖！」
> 在相册里打开 `Tencent-switcher-GUI`，设置为「全球版本」，重启后再升级固件。

出处二：《国行 Switch 20.x.x 系统生存指南》（`tsight.io/articles/17407712`）：

> 「**先转区，后升级**是目前唯一可行的逻辑闭环。」
> 「操作窗口：**19.0.1** 系统版本。」
> 「由于国行设备无法通过官方渠道升级至 20.x.x 系统，因此必须采用**离线升级**的方式。」

这恰好是 §8.1 的实锤反证：**升级的前提是改区域标志，而不是改 DNS。**
那位博主的 19.0.1 与本文实验机同版本，所以「他能升」不等于「换地址能升」。

**一眼分辨真假教程的判据**（出现任一项即说明是破解路线）：

| 教程里出现 | 意味着 |
|---|---|
| 大气层 / Atmosphere / hekate / fusee | 自定义固件 |
| emuMMC / SysNAND / 备份 NAND | 承认有变砖风险 |
| `Tencent-switcher-GUI` / 转区 / 全球版本 | 改的是 §8.1 说的区域标志 |
| 「离线固件包」「整合包」下载 | 系统包来自非官方来源 |
| 「先转区再升级」 | 与官方通道完全无关 |

本文不提供上述任何步骤。原因不是保守，而是代价不对称，见 9.5。

### 9.4 一条未经证实的说法，单独隔离在这里（来源等级：第三方，**未经证实**）

有自媒体（今日头条、网易号，2026-10）称：**23.0.0 修复了一个与「相册扫码传图」
和「马力欧卡丁车 Live 二维码配对」相关的高危漏洞**，所有低于 23.0.0 的机器均受影响。

**该说法未能在任天堂官方更新日志中找到对应原文，标注为未经证实，不要当成事实引用。**
任天堂官方 23.0.0 / 23.0.1 的日志表述为「虚拟游戏卡相关设置变更、在线许可证使用方式调整、
整体稳定性提升」，未提及安全修复条目。

若该说法成立，对国行机的含义是：**这个补丁永远拿不到**。
零成本缓解措施：不在展会、线下聚会、门店等公共场所调出相册的「发送到手机」二维码界面。
居家自用几乎没有被利用的条件。

### 9.5 结论：四条路的代价对比

| 路径 | 成本 | 得到 | 失去 |
|---|---|---|---|
| **就地当单机**（推荐） | 0 | 卡带、已下载数字版、本地联机全部保留 | 线上功能永久缺失 |
| 二手海外版 OLED | 千元级 | 23.x、eShop、联机、云存档 | 需重买数字版（卡带通用） |
| Switch 2 | 三千元级 | 同上 + 新作 | 同上 |
| 破解 + 转区 + 离线刷固件 | 违法、失保、变砖无官方修复 | 23.x、能跑 20/21 门槛的新作 | **机内已下载的国行数字版可能全部失效，且永久无法重下**；§8.3 的证书边界依旧存在 |

最后一行是本文最重要的一句：**代价不对称。** 赌掉的是「已经无法重新获取」的资产，
换来的是「能玩更新的海外卡带」。前者不可逆，后者有更便宜的替代方案。
